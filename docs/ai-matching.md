# AI and matching

## Principles

1. **The match score is computed, not generated.** `app/services/matching/engine.py` calculates it deterministically
   from structured data. A language model is never asked for a percentage.
2. **Missing data is not a mismatch.** A component that can't be evaluated is *not applicable*; the remaining weights
   are renormalized and the UI says what is missing.
3. **Hard requirements stay visible.** They are listed separately and cap the score, so similarity can't hide them.
4. **No sensitive characteristics.** Age, gender, origin, religion, disability and photos are not inputs.
5. **AI output is validated.** Every structured response is parsed into a strict Pydantic model; the CV optimizer's output
   is additionally fact-checked against the source profile.

## Match score (algorithm 1.3.0)

| Component | Default weight | How |
|---|---|---|
| Skills | 0.35 | Required skills count double, preferred once. A skill counts when it is on the profile's skill list **or** appears in a job description of the profile ("from your work experience"). Synonyms are normalized (`JS` = `JavaScript`, `.NET Core` = `dotnet`, …). |
| Experience | 0.25 | Relevant experience = jobs whose title resembles the vacancy or that mention its skills; overlapping periods count once. Score = relevant years ÷ required years (from `min_years_experience` or the level: junior 0, medior 2, senior 5, lead 8). |
| Role | 0.20 | With embeddings: 0.6 × calibrated cosine similarity (profile ↔ vacancy) + 0.4 × title similarity. Without: title similarity + word-overlap similarity of the texts. |
| Qualifications | 0.10 | Highest education level vs. the required level (a professional bachelor counts as bachelor). |
| Preferences | 0.10 | Average of the preferences the candidate set: commuting distance (Belgian place table, haversine), remote/hybrid/on-site, contract type, salary (both sides normalized to EUR per year), industry. |

Weights are configuration (`MATCH_WEIGHT_*`). Overall = Σ(score × weight) ÷ Σ(weights of applicable components).
Fewer than two applicable components, or neither skills nor role applicable → **no score** ("onvoldoende gegevens").

**Hard requirements** (eligibility): required languages (at professional level or better), required education level,
less than half the required years of relevant experience, more than half of the required skills missing. If any is
not met, the score is capped at **60** and the UI explains why. Requirements that can't be checked are shown as such.

**Persistence and staleness**: results are stored in `job_matches` with a hash of every input (profile, preferences,
vacancy, embeddings, weights, algorithm version, current month). A changed hash triggers recalculation on the next read.

**Embeddings**: `nomic-embed-text` via Ollama (768 dimensions, pgvector), computed by the worker when a profile or vacancy
changes. Calibration: cosine 0.45 → 0, 0.80 → 1 (approximate values for this model; adjust in `engine.py` when switching models).

## CV extraction

The text is extracted with pypdf/python-docx; scanned PDFs (almost no text) are reported as needing OCR. The model fills a
flat schema (`services/cv/llm_schema.py`) in which every field is required but may be null: small local models otherwise tend
to return the shortest valid JSON. Dates are normalized, ids are generated by the backend. Without a model, a rule-based
extractor finds contact details, skills and languages and labels the result as basic. Extracted data is stored separately
and only reaches the profile after the candidate confirms it.

## CV optimization

1. **Gather** the verified profile (or a chosen CV version), the vacancy and its skills; check ownership.
2. **Gap analysis** (deterministic): skills present, required/preferred skills missing, skills that are listed but not shown
   in any experience, relevant experiences.
3. **Generate**: the model receives the profile with item ids and the vacancy as delimited, untrusted data, and returns
   `OptimizerOutput`: new summary/headline, an order for experiences/skills/projects, rewritten bullets with `source_refs`,
   questions for the candidate.
4. **Assemble and fact-check** (`services/cv/factcheck.py`):
   - names, employers, titles, dates, education, certifications, languages and contact details are copied from the source;
   - a bullet is kept only if it introduces **no numbers** and **no skills** that its source item doesn't contain;
   - skills are limited to the profile's skills; the summary and headline are checked against the whole profile;
   - anything rejected becomes a **review item**; required skills the profile lacks are listed as gaps;
   - change notes are derived from the actual differences (the model's own notes are only kept for sections that changed).
5. **Recalculate** the match for the original and the tailored CV with the same engine (lexical role similarity for both,
   so the comparison is like-for-like). The UI explains that a different score reflects presentation, not new qualifications.
6. **Store** a new `cv_versions` row: generated content (immutable), editable content, source snapshot, report, both match
   results, provider/model. The candidate can edit, restore, regenerate and export.

Without a configured model, only seeded demo records get a rule-based "simulated" optimization (reordering only), marked
`is_simulated` and labelled in the UI.

## Career assistant

The context contains only the requesting user's profile and up to three vacancies the user can see (with platform match
data). The system prompt treats all of it as untrusted data, forbids inventing facts and claiming actions, and the
conversation is stored per user.

## Prompt injection

Document text, vacancies and user messages are wrapped in `<document>`, `<vacancy>` and `<profile>` tags, and every system
prompt says that instructions inside them must be ignored. More importantly, the model can't do anything harmful with a
successful injection: it has no tools, it only returns data that is schema-validated and fact-checked, and it never sees
other users' data.
